## Dependency notes

- **001 comes first because the repository has no tests, no test runner, and no
  CI.** Plans 002, 003, and 005 all change behavior in `packages/core`; without a
  runner they land unverified. 001 installs Vitest, wires it into Turbo, and
  writes the first ~45 tests against the pure logic that is already testable.
- **002 depends on 001** only for the harness — its sanitizer tests are the whole
  proof that the fix works without breaking legitimate email rendering.
- **003 depends on 001** more strongly than any other plan: its correctness *is*
  its test table of real SMTP replies. Do not ship 003 without 001.
- **005 depends on 001** because the Nodemailer 6→9 jump has no other automated
  signal. Note that even with 001, the live SMTP send path remains untested —
  005 Step 6 requires the executor to say so explicitly rather than imply
  coverage that doesn't exist.
- **004 and 006 are independent** and can run in parallel with anything.
- **004 and 002 compound.** The stored XSS in 002 is a full session compromise
  precisely because there is no session boundary (004). Either one alone reduces
  the impact; both together close it. If only one can be done, do 002 — it fixes
  the injection itself rather than the blast radius.

## Findings noted but not planned

Confirmed by reading the code, judged not worth a plan at this effort level:

- **`getOutboundMessages` is not scoped to a thread**
  (`apps/web/app/(dashboard)/inbox/actions.ts:282-292`). It filters only on
  `status = 'sent'` and `leadId`, so a lead who is in two campaigns sees both
  campaigns' mail in a single conversation view. Real, user-visible, but
  cosmetic; the fix needs a product decision about what a "thread" means here.
- **`replyToEmail` does not escape the reply body**
  (`apps/web/app/(dashboard)/inbox/actions.ts:193` —
  `html: body.replace(/\n/g, '<br>')`). A `<` typed by the operator reaches the
  recipient as markup. Self-inflicted only (single-user app, own input), so it is
  a correctness papercut rather than a vulnerability.
- **Daily-send accounting is optimistic** (`apps/web/lib/scheduler.ts:308`). The
  per-connection sent count is incremented before the send and never rolled back
  on failure, so failed attempts consume daily quota. Bounded in practice: only
  `BATCH_SIZE` (10) messages are attempted per tick and a connection is disabled
  after 3 consecutive failures.
- **Deferred messages are rescheduled by a flat +24h**
  (`apps/web/lib/scheduler.ts:300-304`) when every mailbox is at capacity, rather
  than to the next open send window. Self-correcting on subsequent ticks.

## Findings considered and rejected

Nothing was rejected as a false positive in this pass. Two things that look like
findings but are **by design** — do not re-report them:

- **SMTP passwords are decrypted in the scheduler and reply paths.** This is
  necessary and correct; they are encrypted at rest with AES-256-GCM via
  `packages/core/src/crypto.ts` and never returned to the client. `CLAUDE.md`
  documents the design under "Security Rules".
- **The scheduler and inbox poller run in-process on `setInterval`.** This is a
  deliberate single-process design, documented in `CLAUDE.md` ("Deploy with
  Docker" and "In-Process Scheduler & Inbox Poller") with an explicit warning not
  to scale `web` to multiple replicas. Reporting it as a scalability defect
  misreads the product.
- **`inbound_emails.bodyHtml` stores unsanitized HTML.** Plan 002 sanitizes on
  read, deliberately, so that a later change to the allowlist re-renders old mail
  correctly. Storing sanitized HTML is not the fix.
